# 在 GenAIWorkPipeline 中使用本顾问

用户 2026-09-28 指示：
- 先在 **GenAIWorkPipeline 工作空间内**，对「十二门徒」岩群和「高山圣城城堡」两个场景做**配色**与 **WFC 建模**试做；
- 试做通过后，整条流水线再按这套方法推进；
- TigerMessenger 只读，不修改。

以下都是本项目的工程设计（【推】），不是 Oskar 的私有实现。

## 一、Agent 在流水线中的角色

```
目标图 / 场景约束
  → Oskar 顾问 Agent（本技能）
      ① 诊断：大形、主次、轮廓、承托、通路
      ② 规划：格网与语义层（主体/翼楼/台基/岩台/海蚀基座…）+ 固定边界
      ③ 配色：语义色角色 + 中性日光 / 黄昏两套照明
  → 确定性引擎（Blender 端）
      网格 → 角点状态 → 模块选择（WFC）→ 形变拼接 → 装饰层 → 上色 / 描边
  → 验收：硬检查（接口、承托、净空、连通）
          + 客观相似度 + 同机位灰阶 / 彩色 / 无雾对照
  → Agent 只改少量格子或模块，再渲染
  → Godot 接入（确定性，不经 LLM）：GLB 导入 → 同机位同光照展示场景 + 轨道相机 + 碰撞体
          → 试运行截图，与 Blender 渲染核对（尺寸、同机位 DINO ≥ 0.80）
```

**LLM（Bonsai）不再直接摆坐标**：它输出的是格子状态、语义标签、配色角色和少量参数；几何全部由模块库和确定性引擎生成。

## 二、引擎层（在现有 Blender worker 上扩展）

| 层 | 职责 | 依据 |
|---|---|---|
| 网格 | 六边形 → 随机合并 → 全部细分 → 松弛 → 对偶；按种子确定 | x-timeline §2.1 |
| 状态 | 角点：高度层、语义（岩 / 台面 / 水 / 墙 / 屋 / 路）、材质角色 | 同上 |
| 模块库 | 薄壳角段；邻接从几何边缘自动扫描；允许多格超级模块 | §2.2、§4 |
| 求解 | WFC：局部重算、熵优先、限界回溯；约束包括承托、通路、净空；特殊模块可强制放置 | §2.2、§3、§4 |
| 形变 | 单位立方体顶点 (u,v,w) → 三线性插值；分层平滑（硬边 > 边界 > 材质边） | §4 |
| 装饰 | 门窗、道具另跑一层，保持端正；植被放在不可达或台面上 | §2.3、§3 |
| 表现 | 调色盘上色 + 明度微抖、描边、柔和 AO；无雾检验轮廓 | §2.4 |

## 三、试做 1：十二门徒岩群（配色 + WFC 岩体模块）

- **模块**（先手工样块，再求解）：入水基座、海蚀凹槽、宽低台、陡崖、偏侧上台、破碎冠部；横向接口记录边界曲线、高程、承托，而不只是半径。
- **布局**：3 根岩柱加 1 块相连的低台；2 根独立，1 根与低台相连；台面朝向错开。
- **配色**起点（待验证）：
  - 冷蓝灰岩 `#758694`，湿岩脚更暗；
  - 植被深橄榄 `#596853`；
  - 海水与泡沫层次分开。
- **硬检查**：
  - 岩脚与海面相交；
  - 主要台面宽度 ≥ 局部直径的 20%、坡度 ≤ 15°；
  - 无悬空（最大连通块判定）；
  - 接口无裂缝。
- **视觉检查**：关闭雾后，至少能看出两级宽台面；四分之一环绕视角下不能只剩等宽柱体。

## 四、试做 2：高山圣城城堡（配色 + WFC 建筑模块）

- **样区**：港口上城入口 → 一段台基 → 一个翼楼 → 主体下部。
- **模块**：台基外角、城墙直段 / 转角、拱门（含通路开口）、墙脚、主体墙、翼楼墙、屋顶衔接、塔楼、坡道。
- **规则**：
  - 支撑约束：悬空 → 拱 / 支撑；
  - 围合空地 → 庭院；
  - 门窗另跑装饰层；
  - 城墙必须给通道留出开口。
- **配色**起点（待验证）：
  - 灰米石 `#B1A38E`，旧砖屋顶暗赭 `#925D4D`；
  - 穹顶青灰金属 `#586D73`；
  - 主体明、墙脚与深拱压暗。
- **硬检查**：
  - 港口到城内的路径连通；
  - 台基贴山；
  - 城墙不堵路；
  - 屋顶与墙接缝闭合。
- **视觉检查**：远景主次（主体 > 翼楼 > 台基）清楚；近景承托扎实；灰阶图里主体与背山分得开。

## 五、每轮产出（沿用顾问协议）

1. 画面证据；
2. 固定边界；
3. 模块关系；
4. 资料结论与项目推断，分开标注；
5. 最小试验；
6. 硬检查与视觉检查结果；
7. 种子、模块版本、同机位对照图、回退点。

## 六、实施顺序（需 Extra 推理强度）

1. Blender 端的网格、状态、形变基础层，以及 6 种基本形的白模验证。
2. 岩体模块样块（手工）→ WFC 求解 → 十二门徒试做。
3. 城堡模块样块 → WFC 加支撑 / 通路约束 → 圣城试做。
4. 配色：两套照明 × 彩色 / 灰阶 / 无雾三种同机位图。
5. 用户验收通过 → 接入流水线（新的 `oskar` 建模模式 + Agent 路由）。

## 七、与 Bonsai 协作的提示词套件（已实现：`src/genai_pipeline/oskar/prompts.py`、`agent.py`）

| Bonsai 短板（本项目实测） | 补救（提示词 / 引擎） |
|---|---|
| 空间坐标弱：蓝图时代悬空、比例错 | 只写 5 种原语，平面坐标归一化、高度用层数；悬空自动补台基；塔楼、拱门、城垛由引擎规则涌现 |
| 整图理解与定位弱 | 读图拆成固定问卷（数量 / 左右顺序 / 高宽比 / 台阶数 / 谁最高）；附 SAM 3 实例框作为客观数据 |
| 位置换算凭感觉，主体挤成一团（实测 v1） | PLAN 里给出换算公式：x=(图像x−0.5)×1.8；近 / 中 / 远 → y 区间；r≈图像宽×0.9；层数由高宽比推 |
| 太细的一级成「烟囱」 | 引擎把 r<0.05 放大到 0.05，并把修正写进反馈 |
| 思考耗尽预算、输不出 JSON | 严格字段 + 少样本示例 + 思考预算上限（读图 2048 / 规划 3072 / 评审 2048）+ 带错误信息重试 |
| 自评分虚高 | 评审只列 ≤3 条大形差异，不打分；好坏由客观相似度与硬检查判定 |
| 补丁有效率低（旧流程 16%） | 只允许 6 种受限编辑（move / scale / top / add_tier / remove / add），幅度钳制；客观分升 0.3 以上、且硬检查不退步才接受 |
| 被不合理的检查带偏（实测 v1：3 轮都在修小岩柱的台面） | 检查只对大岩柱（占地 ≥10 格）要求多级台面；评审优先级：硬检查 → 构图 → 主次高宽比 → 台阶 |

| 深层嵌套 JSON 括号数错（实测：评审多写一个 `}`；城堡规划连续 3 次失败） | 解析端按括号栈修复（丢弃多余、补齐缺失）+ 去掉 `//` 注释和尾逗号；评审输出拍平一层；最后一次重试关闭思考 |
| 通路只写一个高度，从海边直接「架」到城门（实测：生成 14 米高的实心石墙） | 只给一个高度时，起点取地面或海面高度，一路做台阶；路下缺地面自动填石成堤道 |
| 把整座悬崖写成台基（实测：渲染成巨大的光面石墩） | 从地面起、高于 3 层的台基自动把下部转为岩崖，只保留顶部 2 层石砌 |
| 建筑放在崖外，地基一直补到海面（实测：塔楼立在海中石柱上） | 深地基下部改用岩体，只有贴着建筑的 2 层用石砌 |
| 不会描述风格细节（实测：城堡成了尖顶童话城堡，不像地中海宫城） | 风格进引擎：调色盘 citadel = 地中海宫城（拱窗、顶层拱廊、平顶栏杆、方形城垛塔、成排柏树）；主楼写一个 roof "dome" 就展开成「平顶 + 鼓座 + 穹顶 + 采光亭」；读图问卷增加塔顶类型、屋顶类型、主穹顶、瀑布位置 |
| 岩柱只会写「几级台阶」（实测：十二门徒成了叠石板） | 岩体默认竖向棱柱风格：竖向棱脊 + 通高裂隙（WFC 竖向约束），层缝减少；Bonsai 不用管 |
| 把铁路高架桥写成带塔楼的城墙（实测：十二门徒前景一道城墙，DINO 只有 0.16） | 新原语 bridge：只写折线和桥面层，桥墩与半圆拱由引擎生成；读图问卷增加 bridges；提示词明确「不要用 wall 代替桥」 |
| 城墙 / 台基画到崖体外（实测：圣城城墙悬空，3 轮都在修） | 城墙（含墙角塔）和台基下方悬空时同样自动补地基：贴着的 2 层石砌，更深的用岩体 |
| 修好硬检查的那一轮因客观分略降被回滚，最佳版本带着硬检查失败 | 接受规则改为硬检查优先：修好了硬检查（当前最佳没过）直接接受；硬检查状态相同时才比客观分 |
| 瀑布没有原语（目标图重点元素漏掉） | 新原语 waterfall：只写起点和方向，引擎沿台地逐级跌落入海、加水潭和泡沫；起点落在城墙上时自动从墙脚流出，小凸起不截断 |

流水线入口：控制台「新建运行」选择 **Oskar 风格场景（WFC 引擎 → Godot）**，阶段为「读图与场景程序 → 引擎构建与迭代 → Godot 场景接入 → 交付打包」。
Godot 工程在 `runs/<运行ID>/godot_project`，玩法写在 `main.gd`（extends `addons/pipeline/oskar_diorama.gd`）。
规划用路由角色 `plan`，评审编辑用 `patch`（默认都是 Bonsai）。
选项：`oskar_rounds`（迭代轮数，默认 3）、`oskar_sam`（是否用 SAM 客观数据）、`oskar_program`（直接给定程序，跳过读图）。


## 八、全流水线推进（2026-09-29，用户验收试做后）

- **场景类项目**（圣城、水晶城、湖沼）默认走 Oskar 模式，旧的拆分组装保留为备选。
- **完整游戏**：
  - 「Oskar 世界」阶段按关键画面生成世界（关键画面按 Townscaper / Bad North 等距小岛风格出图）；
  - 道具和角色用 Bonsai 蓝图建模，并加上 Oskar 统一外观；
  - Godot 的 main.gd 继承 oskar_diorama.gd，在世界上写玩法。
- **单个资产**：导出前加 Oskar 统一外观（平面着色 + 描边）。
- **泛化到莫比斯风格**（水晶城、湖沼）：靠自动配色（SAM 分区取色）加 crystal / tree / rail 桥 / 湖盆（clear）四个补充。Bonsai 自主规划的结果：

| 场景 | Bonsai 最佳版本 | 旧方法（拆分组装） |
|---|---|---|
| 水晶城 | DINO 0.420 / SigLIP 0.768 | 0.337 / 0.731 |
| 湖沼 | DINO 0.523 / SigLIP 0.747 | —— |

| Bonsai 短板（本轮实测） | 补救 |
|---|---|
| 晶柱塔会写成 tower 建筑 | 新原语 crystal；读图问卷增加 crystals / big_trees / vegetation；提示词写明「不要用 tower 代替晶柱」 |
| 细长轨道没法用网格桥表达（网格桥最小 2 米厚，显得笨重） | bridge 的 kind 分 arch / rail；读图问卷里桥分类型 |
| 台面层次检查在奇幻岛屿上误报 | 程序记录 scene_type（从读图来），台面规则只查海蚀岩柱 |
| 游戏世界里玩家走不上 2 米一层的台阶 | 坡道 + Oskar 世界里自动攀台阶；出生点避开坡道 |
