# GenAI Pipeline 本地算力使用手册

适用机器：Mac Studio（M5 Max / 64 GB），项目目录 `/Users/panglaohu/Downloads/GenAIWorkPipeline`。
全部推理、生图、建模、游戏构建都在本机完成，不需要云端账号或 API 额度。

---

## 1. 一分钟上手

1. 打开“终端”，执行：
   ```bash
   /Users/panglaohu/Downloads/GenAIWorkPipeline/scripts/start.sh
   ```
   终端窗口保持打开（关掉终端 = 关掉控制台和正在跑的任务）。
2. 浏览器打开 **http://127.0.0.1:8700**。
3. 等顶栏 “LLM 主力” 变成绿色“就绪”（首次加载约 30 秒）。
4. 点左上角 **＋ 新建运行** → 写需求 → **开始**。
5. 在运行页看进度；到“等待确认”时去 **概念图** 页选图并点 **确认并继续**。
6. 完成后到 **交付** 页下载 zip，或在 **游戏** 页点 **▶ 运行游戏**。

停止：在终端按 `Ctrl+C`。模型服务是独立进程，如需彻底释放内存，先在控制台顶栏点服务 → **停止**，再关终端。

## 3. 新建运行

### 3.1 两种模式
| 模式 | 产出 | 阶段 |
|---|---|---|
| **完整游戏** | 可运行的 Godot 工程 + 全部 GLB 资产 | 规划 → 概念图 → 建模 → Godot 组装 → 试玩验收 → 交付 |
| **单个资产** | 一个 GLB 模型（可接入现有工程） | 规划 → 概念图 → 建模 → 交付 |

### 3.2 需求怎么写（影响最大）
写清楚：**主角/物体的外形、颜色、风格、玩法、镜头、胜负条件**。示例：
> 竹林信使：玩家操控一只低多边形小老虎信使，在竹林空地里收集 5 封散落的信件，全部收集后走到红顶邮筒处完成投递即获胜。第三人称跟随相机，WASD 移动、空格跳跃，屏幕左上角显示已收集信件数。风格明亮、低多边形、玩具感。

建议：
- 资产 3–4 个以内，风格写“低多边形 / 玩具感 / 几何拼块”，本地模型更容易建好
- 机械、建筑、道具效果最好；毛茸茸的写实动物、人物面部最难
- 可上传参考图，模型会参考它规划

### 3.3 选项
| 选项 | 默认 | 建议 |
|---|---|---|
| 推理模型 | 主力 Bonsai | 一般不改 |
| 生图后端 | FLUX（每张约 10 秒） | 需要中文理解时选 Qwen-Image（每张 2–3 分钟） |
| 概念图候选数 | 3 | 想多挑选可设 4–6 |
| 最多资产数 | 4 | 首次试用 2–3 |
| 建模最大轮数 | 8 | 道具 3–4 轮通常够；角色可给 8–10 轮 |
| 验收通过分 | 7.5 | 想更严格设 8–8.5（会多迭代） |
| Godot 最大轮数 | 6 | |
| 审批关卡 | 概念图需人工确认 | 想全自动选“全自动” |

## 4. 运行过程中的操作

### 4.1 确认概念图（默认开启）
运行会停在“等待确认”：
1. 打开 **概念图** 页，看每个资产的候选图（模型已自动选了一张，绿框）。
2. 不满意：点其他候选的 **选这张**；或修改下方英文提示词，点 **重新生成 2 张**。
3. 满意后点 **确认并继续**。

> 目标图决定了后面建模的方向，这一步多花 1 分钟最值得。

### 4.2 追加指示
在 **概览 → 给正在运行的 agent 追加指示** 输入，例如“屋顶颜色改成深绿色”“玩家移动再快一点”。指示在 agent 下一步送达（对 Godot 组装、agent 模式建模最有效）。

### 4.3 暂停 / 取消 / 重跑
- **暂停**：在当前步骤结束后暂停，点 **继续** 恢复
- **取消**：停止本次运行
- **从某阶段重跑**：选择阶段后点 **重跑**。建模阶段重跑时，**已导出的资产会跳过，未完成的资产从得分最高的一轮继续**，不会从头来

### 4.4 各阶段大约耗时（实测）
| 阶段 | 耗时 |
|---|---|
| 方案规划 | 1–2 分钟 |
| 概念图（3 个资产 × 3 张 + 关键画面） | 3–4 分钟 |
| 蓝图建模 | 每轮 4–6 分钟；道具 2–4 轮，角色 6–10 轮 |
| Godot 组装与试玩 | 每轮 10–20 分钟 |

## 5. 看懂验收（JEV System One 式差异迭代）

每轮建模后按下面的顺序走（参考 TigerMessenger 的 Jev 流程，全部在本机运行）：

1. **渲染**：固定 4 个机位——左前方 3/4 俯视（贴近概念图视角）、正面、侧面、右后透视。
2. **观察一次，生成差异台账**：视觉模型看“目标 | 当前”并排对比图，逐条列出差异：部件、类别（剪影/比例/位置/缺失/颜色/多余/细节）、严重度 1–3、可度量的描述。台账与渲染图 SHA256 绑定，渲染变了必须重新观察。
3. **评分由台账计算**：10 分减去未解决差异的权重（严重 2.0 / 明显 1.0 / 细节 0.4），模型不能自由打分；存在严重度 ≥2 的差异就不算通过。
4. **硬性检查**（确定性，不靠看图）：无悬空部件、三角面预算、尺寸量级、**左右对称**（载具/角色）。必需检查未通过时，下一轮强制先处理它。
5. **System One 决策**：开源 **Laya**（本地、离线）从台账里选**一个**工作类别和 1–3 条焦点差异；置信度 ≥ 0.85 直接采用，否则交给 Bonsai 复核（相当于 Jev 流程里的 Astra 复核）。
6. **只改焦点差异**：蓝图修订只动相关部件，其余原样保留；下一轮验证焦点是否消除，退步则回滚到最佳轮，并把这次无效改法写入历史供下次决策避开。
7. **最佳轮**：必需检查全部通过的轮次中得分最高者。

在控制台：**概览 → 模型实时输出** 顶部显示最近一次迭代的对比图；**建模** 页每轮显示对比图、差异台账（`[d1 部件·类别·S严重度]`）和 System One 决策（由 Laya 还是 LLM 复核做出、类别、置信度、焦点、执行计划）。
证据与决策文件：`runs/<运行ID>/jev/<资产>_rNN_{compare.jpg, evidence.json, decision.json}`。
每次决策与其结果会追加到 `data/system_one_dataset.jsonl`，积累到数百条后可用于微调 Laya，让它更懂本项目的建模决策。

试玩验收额外检查：脚本/运行错误、玩家能否在模拟按键下移动、截图画面与关键画面的相似度。

> 评分仍是模型视觉判断的结果；以对比图为准，必要时人工把关。

## 8. 调参（`config/pipeline.toml`）

| 配置 | 作用 |
|---|---|
| `pipeline.model_mode` | `blueprint`（默认，快、稳）或 `agent`（逐步写代码，灵活但慢） |
| `pipeline.model_max_rounds` / `model_pass_score` | 建模轮数 / 通过分 |
| `pipeline.approval_gates` | 需要人工确认的关卡，`[]` 为全自动 |
| `pipeline.agent_max_steps` | agent 每轮最多工具调用次数 |
| `llm.main.mlx_memory_limit_gb` | 主力 LLM 内存上限（**不要删**，否则会越跑越慢） |
| `image.default_backend` | `flux` 或 `qwen_image` |
| `blender.headless` | 改为 `false` 可打开 Blender 窗口实时观看建模 |

修改配置后需重启控制台（终端 `Ctrl+C` 后重新运行 `scripts/start.sh`），**重启会中断正在进行的运行**，之后用“从某阶段重跑”继续即可。

## 9. 常见问题

| 现象 | 处理 |
|---|---|
| 打不开 http://127.0.0.1:8700 | 确认终端里 `scripts/start.sh` 还在运行；重新执行一次 |
| “LLM 主力”一直不是就绪 | 点它看日志；首次加载需要约 30 秒 |
| 运行显示“已中断” | 控制台重启过；点 **从失败阶段重跑** |
| 模型越来越慢 | 看顶栏内存；在服务面板停止再启动“LLM 主力” |
| 屏幕闪出游戏窗口 | Godot 试玩截图，正常，几秒后自动关闭 |
| 概念图不理想 | 在概念图页改提示词重新生成；或关闭“全自动”以便人工确认 |
| 角色模型分数上不去 | 本地 27B 用几何体拼角色的上限约 6–7 分；可换更简洁的风格描述、增加轮数，或人工在 Blender 中精修（`.blend` 在 `blender/blend/`） |
| 模型下载 | `python3 scripts/fetch_models.py`（可断点续传，自动绕过代理直连下载源） |

## 12. 复杂场景：拆分组装模式

新建运行选“复杂场景（拆分组装）”，阶段为：**拆分子资产 → Blender 建模（逐个子资产）→ 场景组装 → 交付**。
1. **拆分**：模型看整张目标图，拆成 3–8 种子资产（如主殿、塔楼、城墙段、崖体、瀑布、连拱桥、柏树），每种给出目标图中的裁剪框、单体尺寸和若干摆放实例。控制台“概览”显示带框的拆分示意图与子资产表。
2. **子资产建模**：每种子资产用裁剪出的局部图作为目标，按单物体蓝图模式迭代（与侦察机相同的方式）。
3. **场景组装**：按布局把子资产 GLB 摆进场景，渲染后与整张目标图对照；System One 决策后只调整摆放（位置/朝向/缩放/数量），成对比较决定保留或回滚。
4. **交付**：`models/scene_composite.glb` + `layout.json` + 各子资产 GLB。

## 13. 迭代轮次与收敛预测

| 配置（新建运行可改） | 含义 |
|---|---|
| 建模最大轮数 `model_max_rounds` | 每个资产最多迭代轮数（上限） |
| 停滞提前结束 `plateau_patience` | 冠军连续 N 轮未被超越就提前结束，默认 6 |
| 场景组装最大轮数 `compose_max_rounds` | 场景模式布局迭代上限，默认 8 |
| 验收通过分 `model_pass_score` | 台账评分达到且无明显差异才通过 |

“建模”页每个资产显示**收敛预测**：当前冠军分、距通过线的差距、最近几轮的提升速度与预计还需轮数；停滞时显示已停滞轮数。
建议：单物体 10–12 轮 + 停滞 5–6 轮；复杂场景不要把整体轮数调到 50，而是用拆分模式，每个子资产 10 轮左右。

## 15. 客观评分（2026-09-27 起）

LLM 评审给的台账分和实际好坏经常对不上：回放 150 轮历史渲染后发现，同一资产内台账分和客观相似度的排序几乎不相关。因此加入了**客观评分服务**：

- 服务：`metrics`（端口 8096，环境 `envs/vision`，模型在 `models/vision/`：SigLIP‑2 看语义和风格，DINOv2 看结构和形状），流水线需要时自动启动，每轮约 1 秒。
- 作用：
  - **选冠军、选最终导出的轮次**：两轮的客观分差超过 0.5 个波动单位时，以客观分为准；差距在这个范围内，才看成对比较和台账。
  - **判断「改好还是改坏」**：写入 System One 历史，Laya 训练数据的标签也更准。
  - **通过线加客观下限**：台账达到通过线，但 DINO 结构相似度低于 `pass_min_dino`（默认 0.25）时，不判通过。
  - **场景组装**：台账分在复杂场景里常饱和到 0，组装冠军改用客观分选。
- 评审只看名称和图片，不再看资产的文字描述；如果评审判断目标图里看不到这个对象，这一轮不判通过，并在日志里提示「可能裁剪错误」。
- 拆分阶段的框选坐标改为 Qwen 原生的 0–1000 格式。
- 相关配置在 `config/pipeline.toml` 的 `[metrics]` 一节。回放工具：`envs/vision/bin/python scripts/replay_metrics.py 运行ID ...`
- 限制：目标图是场景裁剪（混有其他物体）时，相似度的绝对值偏低、信号偏弱，只适合在同一资产内比较；P1 会用 SAM 3 掩码把目标抠干净。

## 16. Oskar 风格场景模式（WFC 引擎 → Godot）

控制台「新建运行」选 **Oskar 风格场景**，必须有目标图（上传参考图，或使用项目目标图）。四个阶段：

1. **读图与场景程序**：SAM 3 先测出主体位置，Bonsai 答读图问卷，再写十来条大形指令（岩柱、台基、主楼、塔楼、城墙、通路）。
2. **引擎构建与迭代**：固定规则的引擎生成几何，包括格网、WFC 墙面模块、城垛、屋顶、岩层、配色和描边，再做硬检查和渲染。Bonsai 看图后提出受限修改，客观分升了才接受，否则回滚。
3. **Godot 场景接入**（不经 LLM，结果固定）：
   - 把最佳版本的 GLB 导入 `runs/<运行ID>/godot_project`；
   - 生成展示场景：机位、光照与 Blender 同源（`src/genai_pipeline/blender/look.py`），轨道相机，日光 / 黄昏两套光照，柔和 AO，地形与建筑带三角网格碰撞体；
   - 试运行并截 3 张图（正面日光、左侧日光、正面黄昏），然后核对：导入无错、脚本与运行无错、截图非空、尺寸与 Blender 导出一致（误差 ≤ 3%）、同机位截图与 Blender 渲染的 DINO 相似度 ≥ 0.80（实测一致时约 0.90）。
   - 任何一项不过，这个阶段就失败，不交付。
4. **交付打包**：交付包里包含 GLB、`godot_project/` 和报告。


## 17. 全流水线统一 Oskar 方法（2026-09-29 起）

所有模式都按 Oskar 方法出图，风格一致。各模式分工：

| **单个资产** | —— | Bonsai 蓝图建模 + Oskar 统一外观 | —— |
| 复杂场景（旧：拆分组装） | 保留备选 | | |

**自动配色**：
- 目标图既不像圣城、也不像海蚀岩柱时（读图 `palette_hint: "auto"`，或新建运行时选「始终从目标图自动取色」），SAM 3 会按岩石、水、建筑、屋顶、穹顶、树、草、晶体分割目标图，各取区域中位色，再派生亮面、暗面和描边色。
- 游戏世界默认用自动配色。

**新增模块**：
- `crystal`：晶柱簇，一根主晶柱加卫星晶柱，塔脚有金铜平台。
- `tree`：大冠树，巨树带板根；`vegetation: "trees"` 时台地上会自动成林。
- `bridge` 的 `kind: "rail"`：细长轨道或廊桥，细梁加细柱。
- 湖盆：先写一个大 stack，再用 `clear` 挖空中间。

**单个资产的 Oskar 统一外观**：
- 导出前自动做平面着色，并加反转外壳描边，厚度按尺寸自适应；描边外壳不投自阴影。
- 关闭方法：选项 `oskar_look: false`。

**游戏世界的可走性**：
- 通路上升一层的地方是一整格长的坡道（约 45°，深浅条纹表示台阶），玩家可走坡度放宽到 50°。
- Oskar 世界里的玩家遇到不高于 2.3 米的台阶会自动攀上（Bad North 式），所以世界处处可达。
- 碰撞只用真实表面，不含描边外壳；灌木、树、水属于装饰物体 `oskar_props`，不做碰撞。

**Godot 世界脚本提供的数据**（`oskar_diorama.gd`）：
- `spawn_point`：出生点，取通路起点附近的平地；
- `walk_points`：可站立点，不含坡道；
- `path_points`：各条通路的点；
- `pick_walk_points(n, min_dist)`：挑选收集物位置；
- `nearest_walk_point(p)`：离某点最近的可站立点。

**选项**：
- `world_rounds`：世界迭代轮数，默认 2；
- `world_program`：直接给定世界程序；
- `oskar_palette`：`auto` 或留空。

## 18. 多场景世界：Oskar 导演模式（2026-10-06 起）

新建运行选择「多场景世界（Oskar 导演）」。这一模式里 Oskar 是创作者本人：它决定世界、亲自调用工具出图、指挥 LLM 在 Blender 里建造、判断每一轮改得好不好，最后把各个场景整合进 Godot。日志里每一次工具调用都记为「Oskar → 工具：做什么」。

| 阶段 | Oskar 做什么 | 调用的工具 | 产物 |
|---|---|---|---|
| 世界构想 `atlas_brief` | 写世界圣经：一句话世界观、2–4 条支柱、语义色彩角色、共享格网/层高/海面、2–6 站旅程（开场 → 上升 → 高潮 → 收束，张力 1–5） | LLM | `atlas/bible.json` |
| 导演出目标图 `atlas_targets` | 高潮场景先画，成为世界母题；每站用同一串风格锁出图，按评审维度逐张打分，与母题比较风格一致性；不够好就写美术指导、改写提示词重画 | FLUX、VLM、SigLIP | 每站目标图 + 维度分；可在「概念图」页人工改选 |
| 逐场景趋近 `atlas_scenes` | 读目标图写场景程序（只定大形），每轮先评分再选动作：受限修改 / 推翻重写 / 宣布完成；按「修硬伤 → 定大形 → 理层次 → 收色彩与世界」推进 | SAM 3、LLM、Blender、DINOv2/SigLIP-2 | 每站最佳程序与 GLB、趋近曲线、工作室手记 |
| 世界整合 `atlas_compose` | 按旅程把场景排成弧线群岛（高潮在顶点），复评色彩统一、节奏、尺度、衔接；只调间距、朝向、相邻顺序 | Blender、VLM | `oskar_atlas.glb`、`world_layout.json` |
| Godot 接入 `atlas_godot` | 整合世界接入 Godot：碰撞、相机、光照，试运行截图与 Blender 核对；各站入口/出口写进 `oskar_scene.json` 的 `journey` | Godot | 展示工程 |

**导演档案**：评审维度与权重、阶段顺序、阈值、风格锁和整合原则写在 `agents/oskar.json` 的 `direction`，在「系统 Agent → 风格档案」可以看到。任务开始时随风格快照固定。自定义 Agent 没写导演档案时继承 Oskar 的档案，自己的风格规则照常生效。

**接受规则**：硬检查优先（修好了就接受，引入新失败就回滚）→ 客观相似度升 ≥ 0.3 且导演分不降超过 0.5 → 客观持平时导演分升 ≥ 1.0。导演分是 VLM 按锚点打的主观分，只在客观持平时起决定作用，或否决“像了却不成立”的修改。收敛条件：导演分 ≥ 7、硬检查全过、DINO ≥ `metrics.pass_min_dino`。连续 2 轮没被接受时，Oskar 先推倒重写一次程序；还不行才收工。

**学习**：
- 本世界内：每站结束后，哪些改法被接受、哪些被回滚写进「工作室手记」，后面的场景读图、评审时都会带上；
- 跨世界：手记保存在 `data/agents/<agent>/journal/`，下一个世界开工时读取最近 4 次的经验。手记只是工具使用统计和导演意见，**不会改变风格规则**；
- 风格规则：勾选“自动复盘”或手动安排学习时，趋近记录、手记和整合结论都会成为证据，生成待审核的学习草稿。

**交付门禁**：每站目标图导演认可（或人工确认）、硬检查、导演趋近分、结构相似度；世界尺度一致、色彩统一、整合导演评审、整合 GLB、Godot 接入与跨引擎一致性。“节奏：高潮场景最高”只是建议项。

**常用选项**：`atlas_scenes`（场景数，默认 3）、`atlas_rounds`（每站最多轮数，默认 4）、`concept_candidates`（每稿候选数）、`atlas_target_rounds`（目标图最多几稿）、`atlas_compose_rounds`（整合排布轮数）。重跑某阶段时已完成的场景会保留；要重做某一站，先删掉 `state.json` 里 `atlas.scenes.<id>`。

**边界**：各站是独立的海盘，暂不生成跨岛桥梁或渡船玩法；整合世界是展示工程，玩法要另写（可读 `journey`）。没有用真实模型跑过一整轮，所以导演分是否校准、轮数是否够用，都要用固定目标先试跑核对。

## 19. 山形地势专题：收分、台缘、波纹、云与夜光（2026-10-06 起）

依据 33 条 Oskar 帖子的学习笔记（`agents/knowledge/oskar/sources/x-terrain-2021-2024.md`），引擎自动完成以下效果，场景程序一般不需要写：

## 20. 场景串成一颗小行星（2026-10-06 起）

多场景世界的“世界整合”阶段默认生成小行星（`atlas_form` 或世界圣经的 `world_form` 为 `planet`；选 `archipelago` 则为平面群岛）：

1. **排布**（`oskar/planet.py`）：岛屿半径按导出尺寸估计；场景沿倾斜的旅程带依次排开，相邻弧长放得下两座岛并留间隔；星球半径既要放下所有场景，又要让单站岛缘角距离约 30° 以内；高潮场景抬高 10° 纬度。
2. **贴到球面**（Blender `compose_planet`）：平面坐标 (x, y, 高度) → 球面（离场景中心的平面距离 = 球面弧长，高度 = 半径增量）；删去各场景海盘与水体侧壁，保留波纹；生成哑光海洋球；相邻站之间不搭桥，由 Oskar 用地势连起来（见第 4 步之后的“地势连接”）。
3. **Oskar 评审**：星球全景 2 张 + 每站转到镜头前的画面（最多 4 张）一起交给 Oskar，按世界维度打分；可用操作：`spacing`（改变星球半径）、`rotate`（场景绕法向转）、`nudge`（沿东 / 北移动，米）、`swap`（交换相邻两站）、`link`（改某段连接的地势类型 / 宽度 / 垭口高低，下一轮重建这段地形）。
4. **Godot**：`oskar_scene.json` 带 `planet`（球心、半径），云在球壳上绕倾斜轴流动、朝向球心、遇高峰抬升；海洋球不做碰撞；各站中心 / 入口 / 出口与地势连接上的通路都换算到球面坐标；连接地形可碰撞。

### 地势连接（2026-10-06 起，替代陆桥）

参考 Oskar 的“大地势生成 / 复杂地势生成”：场景之间是地势协调出来的，不是桥。整合时每一段相邻连接：

1. **读岛缘**（`planet.link_specs`）：在两站各自的平面坐标里朝对方看，取连接轴线附近最外侧的可站立地面，得到岛缘离中心的距离、高度（换算成层）与两岛缘之间的海面间隙；连接地形的切平面放在间隙正中，本地 +x 指向下一站。
2. **Oskar 选地势**（`director.plan_links`，LLM 不可用时按规则）：`terraces` 阶梯台地（落差 ≥ 3 层）、`ridge` 山脊垭口（两端都高）、`isthmus` 低地地峡（两端都低 / 需要喘息段），并给宽度（7–18 米）与垭口偏移；世界圣经的 `link_to_next` 可写这三种或 `auto`。
3. **引擎生成**（`planet.link_program` → `blender_build_oskar` → 导出 GLB）：与各站同一种场景程序、同一格网与层高、沿用前一站的调色盘；两端台地伸进岛缘 7 米、顶面对齐岛缘高度；通路按台阶 / 坡道接两端；收分、轮廓软化、草唇与灌木都由引擎照常生长。
4. **贴到球面**：连接 GLB 作为 `kind: "link"` 的条目与各站一起交给 `compose_planet`（去海盘、同一投影），旧版陆桥不再生成。

边界：玩家在球面上行走需要指向球心的重力，当前玩家控制器仍是平面重力。


## 21. 岩体与草地的色彩可能性空间（2026-10-06 起）

参考 x.com/OskSta 2023-10-11 “palette authoring tool”：一个特征的颜色是由节点 / 渐变 / 三角张成的空间，每个面在里面取一个点。
`oskar/tint.py` 在构建时逐面取色：

- 岩体（rock / rock_alt / rock_dark / rock_top）：色场 = 视频四个颜色节点（灰绿 #5F8F6A、橙 #D5A157、蓝 #4B8598、玫瑰 #AE6874）的浅调；纵向铺色——每座山（每根岩柱）从自己的山顶往下取色：橙 → 玫瑰 → 灰绿 → 蓝（山脚、水线），横向只有很小的色相偏移；所有场景的山体与地势连接都用这一方式；朝天面与亮层带向米白靠，层纹明暗交替，悬挑压暗；逐面平涂、不加随机。
- 草地同样纵向：从山顶往下 黄绿 → 橄榄 → 草绿 → 青绿；石料、灌木、柏树只做轻微逐面抖动。
- Blender 把颜色写进逐角颜色属性 `Col`，材质基色接颜色属性，导出为 glTF `COLOR_0`；不变化的角色写白色，Godot 导入后按“基色 × 顶点色”着色，颜色不变。
- 场景程序可写 `"tint": 0` 关闭，`0–2` 调强度（默认 1）。地势连接与各站共用这套取色。

边界：色场角点由调色盘自动派生，不能手调节点。

## 22. 本地 FAL 兼容服务：让 image-blaster 等工具用本机 Bonsai + Flux（2026-10-06 起）

有些外部工具只认 fal.ai 的接口（例如 `~/Downloads/image-blaster`）。`genai_pipeline.fal_shim` 在本机 `127.0.0.1:8095`
模拟 fal 的队列接口，**不需要真实密钥**（调用方的 `FAL_KEY` 填占位值 `local` 即可，本服务不校验，也不会生成任何密钥）。

- 图像编辑 / 文生图端点（`fal-ai/nano-banana-2/edit`、`openai/gpt-image-2/edit`、`fal-ai/flux/*` 等）：
  Bonsai 看输入图和编辑指令，写出“改完之后的画面描述”，再交给 Flux 以原图为底图做图生图（重绘强度默认 0.6，`--strength` 可调）。
  Bonsai 没开时直接用原指令；`--no-bonsai` 可关掉改写。
- 图生 3D（hunyuan / meshy）、音效（elevenlabs）、World Labs Marble：本机没有对应模型，返回 501 并说明原因——这些步骤仍需真实服务。
- Flux schnell 图生图是“按描述重画”，不是精确局部编辑：去掉物体、换材质能做到大概，保持细节一致性不如 nano-banana。

## 23. 场景（图生 3D）：参考图 → 拆资产 → Hunyuan3D → Blender 整理组装（2026-10-16 起）

借鉴 Sac《手把手教你用 Opus 5.5 / Astra + Tripo 制作 3D 游戏》的场景构建流程，全部用本机算力：大脑仍是 Bonsai，
Tripo 换成开源的 **Hunyuan3D-2mini Turbo**（只生成形体，配色交给 Blender 按参考图投影取色）。

**安装**：双击 `scripts/setup_shape3d.command`（`scripts/setup.sh` 也会调用）。建 `envs/shape3d`、拉 `vendor/Hunyuan3D-2`、
下载约 4.2 GB 权重到 `models/shape3d`，最后自检生成一次（M 系列 GPU 约 20 秒）。脚本会读取系统代理（如 Clash）。

**使用**：「发起创作」选「场景（图生 3D）」，上传参考图或选一个带目标图的项目（例：`projects/little-prince`）。

| 步骤 | 做什么 | 说明 |
|---|---|---|
| 拆分 decompose | Bonsai 看参考图，列出子资产（尺寸、摆放、英文分割提示）、估计参考机位；SAM 3 找出每类的实例并抠图 | 每个资产标 `method`：远景层（云海/海面/远山）`backdrop`；大面积地面/台地/岛体 `terrain`；其余（角色、家具、建筑、植物、道具）`image3d` |
| 建模 model · image3d | 有掩码且裁剪够大（长边 ≥ `min_crop_px`）用参考图抠图；否则先用 FLUX 单独出一张「单物体、纯灰底」资产图 → Hunyuan3D 按不同种子出 N 个候选 → Blender 整理。裁剪图全失败自动改用资产图再试，仍失败退回蓝图，不中断流水线 | 整理 = 按剪影选正面朝向、缩放到 `size_m`、精简到面数预算、按参考图投影取色并量化成少量色块、落地居中、Oskar 描边。薄片（把背景当物体）自动拒绝换种子 |
| 建模 model · terrain | Oskar 引擎按该资产的参考裁剪读图、写场景程序、构建，受限修改（默认 2 轮，客观分升才接受），再缩放到 `size_m` | 自带收分、台缘草唇、灌丛带、岸线波纹、描边；引擎硬检查写进质量验收 |
| 建模 model · backdrop | Blender 在 `size_m` 范围铺一片起伏的低模团块，颜色按深度从参考裁剪的上（远）到下（近）取样 | 只负责氛围与地平线；组装取景时忽略它，主体仍能填满标准机位 |
| 建模 model · blueprint | 只在 Agent 关掉图生 3D 工具时，道具退回蓝图建模 | 轮数压短（默认 3 轮、连续 2 轮无进步即停） |
| 候选挑选与评审 | 客观相似度（DINO/SigLIP）挑最像的候选，独立评审员看三视角出差异台账 | 评审分写进质量验收 |
| 组装 compose | 按拆分的摆放组装，先按**参考机位**（拆分时估计的相机位置、视场角、画幅）渲染，再加三个标准机位；背景色取参考图上部平均色；评审员找差异，LLM 只改摆放 | 默认 4 轮 |

**调参**：`config/pipeline.toml` 的 `[shape3d]`（`steps`、`octree`、`candidates`、`blueprint_rounds`、`patience`、
`compose_rounds`、`terrain_rounds`）；单次运行可在表单里改「图生 3D 候选数」「建模最大轮数」「停滞提前结束」「场景组装最大轮数」。
Agent 配置里关掉「Hunyuan3D 图生 3D」工具后，该 Agent 的所有资产改走蓝图。

**当前限制（如实记录）**：
- 只出形体，不出贴图；颜色来自参考图正面投影，背面沿用正面颜色。
- 天空本身不建模，组装渲染用参考图天空的平均色作背景；云海、海面等远景层是低模团块，只表达氛围。
- 大面积地形改由 Oskar 引擎生成（2026-10-16 起，此前用蓝图搭草坡只有 0–3 分）；引擎按裁剪读图，裁剪太碎时读图会不准。
- 角色被前景物体遮挡时（如小王子被椅背挡住），抠图有空洞，生成的形体会受影响；最好把角色与椅子作为一个资产。
