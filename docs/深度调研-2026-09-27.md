# 深度调研：本地建模模型、场景拆分核查、流水线重新规划

日期：2026-09-27　｜　机器：Apple M5 Max，64GB 统一内存，40 核 GPU，磁盘剩余约 300GB
范围：只做分析，不改代码。结论里的数字，凡来自本项目运行记录的都注明了运行 ID，凡来自外部的都列在文末来源。

---

## 结论先行

1. **本机模型**：Bonsai 不是天花板，但**模型也不是当前最大的瓶颈**。
   - 值得客观 A/B 的只有两个：
     - **Qwen3.8‑27B 高精度版**：已经装好的 oQ6，不用下载。Bonsai 是它的 2‑bit 三值压缩版，在长流程智能体 / 编码任务上只保留了约 75% 的能力。
     - **Gemma 4 31B 稠密版**：3DCodeBench 人工偏好排行里开源第一，和 GPT‑5.4 Mini 持平，比我们测过的 26B‑A4B 高一截。
   - 本机放不下的超大模型（GLM‑5.3、DeepSeek V4 等）不考虑。
2. **拆分核查**：拆出来的「子资产类别」大体合理，但**框选和裁剪不可靠**。
   - 水晶城 7 个子资产里，3 个框错或框偏；圣城 8 个里 1 个明显框偏，还漏了占画面很大比例的「城区建筑群」和「阔叶植被」。
   - 更严重的是评审给错误的结果打高分：
     - 玻璃穹顶生态舱：裁剪图里根本没有穹顶，却拿了 8.0 分并「通过」；
     - 晶柱塔：模型是一根圆柱加 8 根悬空细锥，拿了 8.6 分。
3. **最大瓶颈是评分，不是建模**。
   - 子资产评分虚高，场景评分又直接饱和到 0，冠军选择、通过判定、交付门槛都建立在不可靠的分数上。
   - 多轮补丁的收益很低：142 轮补丁里只有 16% 刷新了最佳分。
4. **重新规划的方向**：
   - LLM 只负责「导演 / 质检 / 装配」，几何形状交给专门的图生 3D 模型或程序化生成；
   - 评分以客观度量为主（图像特征相似度 + 轮廓 + 硬检查），VLM 只负责指出「改什么」；
   - 在拆分、概念图、交付这几个节点设人工确认；
   - 迭代从「一稿改很多轮」改成「多出几稿择优 + 少量补丁」。

## 一、本机能部署、适合指挥 Blender 的模型（问题 1）

### 1.1 业界 2026 年的评测结论

| 评测 | 与我们相关的发现 |
|---|---|
| **3DCodeBench**（2026‑06，Blender 5.0 程序化建模，212 类物体） | 人工偏好 Elo 排名里，开源模型只有 Gemma 4 上榜：**Gemma 4 31B = 921**，和 GPT‑5.4 Mini（920）持平；Gemma 4 26B‑A4B = 828。<br>多轮报错反馈能把「代码能跑通」的比例从 70% 提到 97%，但包一层编码智能体外壳，**形状质量几乎没有提升**。<br>主要失败模式是**部件互不相连、悬空**，和我们遇到的完全一样。<br>SigLIP‑2 / DINOv3 渲染图相似度与人类偏好的相关系数 r≈0.96（这是模型级汇总，单个资产上噪声会更大）。 |
| **3DHarnessBench**（2026‑09） | 开源模型里测了 Qwen 3.8 Max、Kimi K3、MiniMax M3，全部落后于闭源。<br>**观察质量比 3D 推理更重要**：把截图视角规范化，能明显拉回较弱模型的表现。<br>补充相机位姿、给出部件尺寸测量，几乎所有指标都能提升。<br>「初稿能力」和「迭代修改能力」是两种独立的能力。 |
| **P3D‑Bench**（2026‑06） | 多部件组装比单件难得多；即使 GPT‑5.5，部件匹配 F1 也只有约 0.5。多轮迭代平均只提升 +0.034，有的模型反而退步。 |
| **aDSL**（2026‑08） | 让智能体用**关系式算子**（放在…上、贴合、对齐）而不是绝对坐标去摆几何体，效果明显好于直接写 Blender Python。我们现在的蓝图 DSL 仍然大量用绝对坐标 `at`。 |

### 1.2 候选模型（64GB 内存以内）

| 模型 | 本机体积 | 编码 / 智能体 | 3D 建模证据 | 视觉 / 框选定位 | M5 Max 速度 | 结论 |
|---|---|---|---|---|---|---|
| **Ternary Bonsai 2 27B**（现用） | 5.9GB | 平均保留 Qwen3.8 的 98.2%；但 **Terminal‑Bench 52.8 对 69.7、SWE‑bench 60.8 对 80.6**（约 75%）；不支持低推理强度 | 无 | 视觉保留 96.3% | 约 47 tok/s（实测 40–44） | 快、省内存，但恰好在「长流程编码」上掉得最多 |
| **Qwen3.8‑27B**（已装 oQ6 约 22GB） | 17–28GB | 智能体指数 51；工具调用排第 14/105 | 同系列的 Qwen 3.8 Max 在 3DHarnessBench 里是开源最好 | **框选定位强**（同系列 3.6‑27B 在 RefCOCO 上 92.5%） | 15–30 tok/s | **首选 A/B 对象**。注意默认推理强度是 xhigh，会过度思考，要调低 |
| **Gemma 4 31B 稠密版**（未装） | 约 18GB（4‑bit） | 通用强 | **3DCodeBench 开源第一（921）** | 中上 | 约 20–30 tok/s（估算） | 值得下载一试；我们测过的 26B‑A4B 在同一榜上低 93 分 |
| Gemma 4 26B‑A4B（已装） | 16GB | 不会主动发工具调用 | 828 | 评分离散大 | 约 60 tok/s | 已评测，你判定不如 Bonsai |
| Muse Glimmer 30B / Nemotron 3.5 Lightning / Granite 4.2‑30B（2026‑08 新发） | 约 18GB | 主打智能体 | 无 | 部分支持 | — | 没有 3D 证据，优先级低 |
| GLM‑5.3‑Flash（320B）、DeepSeek V4 Flash（284B） | 90GB 以上 | 很强 | — | — | — | 64GB 放不下 |

### 1.3 建议

- **不要指望换个本地模型就有质变。** 所有 2026 年的评测都显示，开源模型和前沿模型在 3D 建模上仍有明显差距，而且差距主要在「形状准不准」，不在「代码能不能跑」。
- **下一次 A/B 必须换评分方式。** 上次 Gemma 对 Bonsai 的比较，评分员就是 Bonsai 自己；它和 Claude 评分的平均误差有 2.15 分，本身不可靠。新的 A/B 应该用客观度量（见 3.3），再加你人工看图。
- A/B 对象：Bonsai、Qwen3.8‑27B oQ6（已装，零成本）、Gemma 4 31B（下载约 18GB）。按角色分别比较：拆分框选、蓝图初稿、补丁。
- **拆分和框选这个角色建议优先试 Qwen3.8 高精度版**：定位是 Qwen 系列的强项，而 2‑bit 压缩对精细视觉任务损伤最大。

组装阶段 7 轮的分数是 0.0 / 0.0 / 3.2 / 0.4 / 0.0 / 0.0 / 0.0。场景评审其实是诚实的，正确指出了「塔群只有一座塔」「岩岛只是一块多边形」。**子资产评分虚高、场景评分如实，两者互相矛盾**，这本身就证明子资产这一层的评审失效了。

### 2.2 圣城旧城（20260926-052333-01a2）

- 8 个类别（主殿、穹顶塔楼、城墙、崖体、瀑布、柏树、连拱桥、角楼）基本合理。
- **柏树框偏**：框内大部分是城墙和后方建筑，树只占一小条。柏树最终只有 3.0 分，和这个直接相关。
- 主殿只框到上半部分。
- **漏拆**：画面里面积最大的其实是「层叠的城区建筑群」和「阔叶灌木 / 树丛」，都没有作为子资产。
- 组装冠军最后只有 3.0 分，已被交付门槛拦下。

### 2.3 根本原因

1. **框选是单次 VLM 输出，没有任何核验。**
   - 坐标要求的是 0–1 小数，而 Qwen 系列视觉模型原生训练的是 0–1000 相对坐标；
   - 执行拆分的是 2‑bit 压缩的 Bonsai，精细定位最吃亏。
2. **每类资产只给 1 个框、没有实例清单。**
   - 组装阶段拿不到「有几个、各在哪」，只能让 LLM 从零猜布局；
   - 这也是组装分数一直在 0 附近的重要原因。
3. **裁剪图直接当目标图。**
   - 裁剪图有遮挡、分辨率低、混入别的物体，还会和资产定义冲突（一个塔 vs 一群塔）。
4. **评审提示里带着「名称 + 文字描述」。**
   - 图对不上时，评审就退回按文字打分，导致给错误目标打出 8 分以上。
5. **台账评分公式在复杂场景里没有梯度。**
   - 差异超过约 8 条就封底为 0，分不出好坏；
   - 成对比较的判断又常和台账分数矛盾：第 3 轮 3.2 分被判输，第 4 轮 0.4 分反而成了冠军。
6. **拆分结果没有自动核验**，错误的拆分会直接消耗几个小时的建模时间（改为 SAM 实例分割 + 掩码置信度自动核验，不加人工确认）。

## 三、如果重新规划流水线（问题 3）

### 3.1 用数据说话：现有做法的三个根本问题

1. **评分不可靠**：Bonsai 评审和 Claude 评分的平均误差 2.15 分；子资产拿到 8.0 / 8.6 的其实是错的物体；场景评分又饱和到 0。
2. **多轮补丁收益低**：全部 21 个资产共 142 轮补丁，只有 23 轮（16%）刷新了最佳分。最佳结果在第 1 轮的有 9/21，在前 3 轮的有 15/21。每轮约 5 分钟，大部分算力花在了无效修改上。
   - 平均提升看起来有 +1.4 分，但「从一组有噪声的分数里取最大值」本身就会虚高，真实提升更小。
3. **用基础几何体拼模型有天花板**：树、岩体、晶簇、瀑布这类有机或复杂形体，用 10–40 个几何体拼不出来；莫比斯插画风格更是远超这个表达能力。业界做游戏资产的主流流水线是：概念图 → 图生 3D → 部件分割 / 减面 / UV / 贴图（例如腾讯 Hunyuan3D Studio），不是让 LLM 摆几何体。

### 3.2 新架构（v2）

原则：**LLM 当导演和质检员，不当雕塑师；分数以客观度量为准；只用本机算力。**

```
目标图
 └─① 场景解析：Qwen3.8 列出类别（0–1000 坐标）→ SAM 3 按文字分割「所有实例」
      → 得到每类的实例掩码、框、数量（不设人工确认，直接进入建模）
 └─② 子资产干净目标图：按掩码抠图 → 图像编辑模型（FLUX Kontext / Qwen‑Image‑Edit）
      补全被遮挡部分，生成白底、3/4 视角的干净概念图 → 【人工挑选】
 └─③ 按资产类型分三条路生成几何：
      a 有机 / 复杂（树、岩、晶簇、瀑布）：图生 3D（Hunyuan3D‑2.1 MLX / TRELLIS.2 MLX）
        → Blender 减面、平直着色、清理
      b 硬表面 / 建筑 / 低多边形（塔、墙、桥、飞机）：保留蓝图 DSL，改成关系式摆放
        → 先出 4 份初稿择优，再最多 3 轮补丁
      c 大量重复小件（灌丛、花、城垛）：程序化工具包（几何节点 / 散布）
 └─④ 评分：渲染图 vs 目标图的 DINOv3 / SigLIP‑2 相似度 + 掩码轮廓 IoU + 硬检查
      （接触链连到地面、尺寸、面数）；VLM 差异台账只决定「下一轮改什么」
 └─⑤ 组装：SAM 实例位置 + 单目深度估计反投影，得到初始布局；LLM 只做微调；
      组装分用客观相似度，保证有梯度
 └─⑥ 交付：deliver_min_score 门槛（已上线）+ 【人工确认交付】
```

### 3.3 关键组件：本机可行性

| 组件 | 选型 | 本机情况（据来源） |
|---|---|---|
| 实例分割 | SAM 3 / 3.1（mlx-community/sam3-image） | 已有 MLX 移植，支持用文字提示分割所有实例 |
| 图生 3D 形状 | Hunyuan3D‑2.1 MLX | 形状 + PBR 贴图都已移植；FP16 峰值约 10GB，INT4 约 4GB；形状约 2–5 分钟；输出约 50 万面，会重网格到约 4 万面 |
| 图生 3D（备选） | TRELLIS.2 MLX | 技术预览；峰值 3–5GB；M4 Max 全流程约 8.6 分钟、预览约 3 分钟 |
| 客观评分 | DINOv3 / SigLIP‑2 | 小模型，秒级；TRELLIS.2 MLX 里已经有 DINOv3 的 MLX 实现 |
| 干净概念图 | FLUX.1 Kontext / Qwen‑Image‑Edit（mflux） | mflux 已支持图像编辑 |
| 布局初始化 | 单目深度估计（如 Depth Anything 系列） | 需确认有没有 MLX 版本 |

内存：以上都按顺序串行调度，峰值不超过现在 44GB 的预算（Bonsai 6GB + 图生 3D 约 10GB + SAM 约 3GB + FLUX 约 8GB）。

### 3.4 迭代与评分规则的变化

- **多稿择优代替反复补丁**：每个资产先生成 N 份初稿（蓝图路线 N=4；图生 3D 用不同随机种子出 N=2–3 份），用客观分挑最好的，再最多补 3 轮，不提升就停。3DHarnessBench 也发现初稿能力和修改能力是两回事，本地模型的初稿能力相对更可靠。
- **评审不再给文字描述「兜底」**：评审只看图，不看资产描述；如果裁剪图里检测不到目标物体（SAM 置信度低），直接判「目标图无效」，退回拆分这一步。
- **组装评分要有梯度**：用客观相似度打分，台账只列前 5 条差异，不再扣到 0。
- **人工闸门**：拆分阶段不设人工确认；交付前由 deliver_min_score 门槛把关。

### 3.5 分阶段路线（先做收益最大、风险最小的）

执行安排：P0、P1 直接做；开始 P2 前暂停，切换到 Extra 推理强度再做。模型只看能否本机部署，不考虑许可证。

| 阶段 | 内容 | 验证方式 |
|---|---|---|
| **P0 修评分** | 接入 DINOv3 / SigLIP‑2 客观分；评审去掉文字描述兜底；拆分坐标改为 0–1000；做「拆分审查页」和人工确认；组装评分改为有梯度 | 用水晶城、圣城已有的各轮渲染图回放打分，看新分数和你的判断是否一致 |
| **P1 拆分可靠** | 接入 SAM 3 实例分割；生成干净的子资产概念图；用客观分对 Bonsai / Qwen3.8 / Gemma 4 31B 按角色 A/B | 重跑水晶城拆分，逐框人工核查 |
| **P2 几何升级** | 接入 Hunyuan3D‑2.1 MLX（先只做形状）+ Blender 低多边形化；按资产类型分三路；多稿择优 | 先拿柏树、晶簇、岩岛这三类最难的有机资产，和现在的蓝图结果对比 |
| **P3 组装** | 深度估计反投影做布局初始化；实例级放置 | 水晶城、湖沼整场组装 |

### 3.6 风险

- 图生 3D 的 MLX 移植都是社区项目，偏技术预览，可能要自己修问题。
- 输入是莫比斯风格插画，不是照片或干净渲染图，图生 3D 的效果要实测才知道。所以第②步生成「干净概念图」很关键。
- 图生 3D 出来的是稠密网格。要做成低多边形游戏资产，还需要 Blender 减面 / 重拓扑；这一步可以交给现有的 Blender MCP 工具。
- 客观相似度和人类偏好 0.96 的相关，是在模型级别上汇总得出的；单个资产上仍需多视角取平均并人工抽检，不能完全替代人眼。
