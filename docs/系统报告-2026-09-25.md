# GenAI Pipeline 系统报告（2026-09-25）

本机本地算力游戏构建流水线的首日搭建与实测结果。所有数字均来自真实运行（`runs/` 目录可复查）。

## 1. 结论

- **整条流水线已在本机端到端跑通**：需求 → 方案 → FLUX 概念图 → Blender 建模（渲染-视觉验收-迭代）→ Godot 组装 → 试玩验收 → 交付，全程本地，零云端调用。
- **机械/道具类资产效果好**：侦察机 2 轮 8.0、红顶邮筒 1 轮 8.0，单轮 3–5 分钟。
- **角色类资产是当前短板**：小老虎 10 轮最高 6.5（本地 27B 用几何体拼角色的上限）。
- **Godot 能自动产出可玩游戏**：竹林信使可移动、跳跃、收集信件、显示中文 HUD，0 脚本错误、111 FPS；但画面与 FLUX 关键画面差距大（试玩视觉分 3.0），组装每轮较慢（10–25 分钟）。

## 2. 硬件与模型

| 项 | 配置 | 实测 |
|---|---|---|
| 机器 | Mac Studio M5 Max，64 GB 统一内存 | GPU 可用约 48 GB |
| 主力 LLM | Ternary Bonsai 2 27B（MLX 2-bit，8.6 GB） | 解码 40–44 tok/s，预填充约 650 tok/s；工具调用、看图正常 |
| 兜底 LLM | Qwen3.8-27B oQ6（MLX，23 GB） | 解码约 23 tok/s；工具调用、看图正常 |
| 主力生图 | FLUX.1-schnell（mflux 4-bit） | 首张含加载 30 s，之后约 10 s/张 |
| 兜底生图 | Qwen-Image 2.1 Q6_K（sd.cpp） | 可直接用中文提示词；768²/20 步 191 s（与 LLM 并发） |
| 建模 | Blender 5.2.2（后台 worker） | 3 视图 EEVEE 渲染约 2 s |
| 游戏 | Godot 4.7.2 | 导入、检查、带模拟输入试玩截图约 10 s |

模型全部经 SHA256 校验，共约 53 GB（`python3 scripts/fetch_models.py --status`）。

## 4. 搭建过程中发现并修复的问题（均已验证）

| # | 问题 | 影响 | 修复 |
|---|---|---|---|
| 1 | 本机代理下 HF CDN 仅 0.02 MB/s，xet 断流 | 模型无法下载 | 自写多连接直连下载器，断点续传 + SHA256 |
| 2 | MLX 缓冲缓存无上限，涨到 49 GB | 解码从 44 掉到 8 tok/s | 启动器设置 20 GB 内存上限 / 4 GB 缓存上限 → 占用 10 GB |
| 3 | 前缀缓存命中后解码走慢路径 | ~20k 上下文解码 14 tok/s | 关闭前缀缓存，改为压缩历史 + 每轮全新上下文 |
| 4 | agent 模式逐步写 bpy 代码 | 每轮 25–40 分钟，角色 2.5–3 分，常推倒重来 | 新增**蓝图建模**（结构化部件清单 + 确定性构建）：每轮 4–6 分钟，角色 6.5、机械 8.0 |
| 5 | 同样输入产生同样输出，回退后原地打转 | 连续 3 轮完全相同的 4.0 分 | 每次请求随机 seed + 记住失败尝试 |
| 6 | 代码出错留下半成品、API 误用 | 大量失败步 | 执行原子回滚、参数容错、常见误用直接可用、报错附提示 |
| 7 | 部件悬空、组装错位 | 模型零散 | H.snap / H.limb / H.capsule 等助手 + 悬空检测 |
| 8 | 渲染灯光过曝 | 颜色评审失真 | 色卡校准灯光（测试守护） |
| 9 | Godot 手写 Mesh 代码易错、改坏后无法恢复 | 试玩 0–1 分 | Kit 工具箱（玩家/收集物/触发区/竹子/散布/HUD）+ 每轮快照与自动回退 + 结束时保留最佳轮 |
| 10 | Godot 默认字体无中文 | HUD 显示方块 | 工程内置 Noto Sans CJK SC（OFL）并设为默认 UI 字体 |
| 11 | 兜底模型未下载时仍切换，空等 15 分钟 | 运行失败 | 可用性检查后才切换 |
| 12 | 控制台重启后不认识旧服务进程 | 内存预算失控 | 按端口接管已有服务 |
| 13 | 中断后只能从头来 | 浪费时间 | 建模/组装都支持从最佳轮续跑 |

自动化测试 11 项（假 LLM 驱动真实 Blender/Godot）：`.venv/bin/python -m pytest -q` 全部通过。

## 5. 当前能力边界

| 方面 | 现状 | 建议 |
|---|---|---|
| 机械、建筑、道具 | 1–3 轮可达 7.5–8 | 可直接用于 TigerMessenger 的道具/载具/建筑类资产 |
| 角色、动物 | 约 6–6.5 封顶 | 作为白模/占位；精修需人工或引入图生 3D 模型（需另行决定） |
| 视觉评分 | 机械类略宽松，场景级严格且有波动 | 以渲染对比为准；通过分可调到 8–8.5 |
| Godot 组装 | 能做出可玩原型，每轮 10–25 分钟，偶尔改坏（已自动回退） | 适合“新建玩法原型”；接入 TigerMessenger 现有大场景需新增“现有工程模式” |
| 速度 | 概念图快；建模每资产 10–40 分钟；组装最慢 | 小批量、先机械类 |

## 6. TigerMessenger 真实场景试用建议

TigerMessenger 当前以 Web（three.js）为主，Godot 为同步工程（`godot/`，渲染器 GL Compatibility，主场景 `test_hub.tscn`，有 `scout_candidate.tscn`、`tiger_anatomy_candidate.tscn` 等资产检视场景）。流水线的原则：只读原工程、在副本上工作、接入需人工确认。

| 候选 | 内容 | 预期 | 需要的开发 |
|---|---|---|---|
| **A. 侦察机资产（推荐首试）** | 用认可的 `scoutAircraft-target-v1.png` 重做侦察机 GLB，接入 `godot/assets/pipeline/`，在 `scout_candidate` 场景的副本中同机位对比截图 | 机械类强项，预计 8 分以上 | 小：增加“在现有工程副本中挂载资产并截图”的步骤 |
| B. 古松 / 场景道具 | 按 `ancient-pine-target-v1.png` 生成古松，接入场景副本 | 植物类中等 | 同 A |
| C. 小老虎角色 | 按新虎目标图重建 | 角色弱项，约 6 分 | 同 A；可能需人工精修 |
| D. 现有 .blend 迭代 | 以原 .blend 为源、agent 模式修改 | 依赖原模型结构 | 已支持（源模型路径），需选定资产 |
