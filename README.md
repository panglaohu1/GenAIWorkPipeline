## 本轮新增

### 2026-10-06 总览：从目标图到星球游戏

今天做完并写回本机的内容，按使用顺序排列。

**一句话流程**：Oskar 构想世界 → 用 Flux 画每一站的目标图并打分 → 按目标图逐轮在 Blender 里趋近 → 场景贴到一颗小行星上、用地势连起来 → 生成能玩的 Godot 星球游戏 → **先游玩测试，再下载与发布**。

#### 1. 目标图驱动的多场景世界（Oskar 导演）

- 阶段：世界构想 → **导演出目标图**（Oskar 调本机 Flux，flux1-schnell 4 步，每站多张候选，按导演档案维度打分、选图、不达标改写提示词重画；事件流显示「Oskar → FLUX.draw」）→ **逐场景趋近**（每轮 Blender 构建、渲染，与目标图比 DINO / SigLIP，Oskar 给维度分，按规则接受或回滚，收敛或停滞即停）→ 世界整合 → Godot 接入。
- 修复（2026-10-06）：模型把世界圣经里的文字字段写成数组（如 `palette.roles: [...]`）时，出目标图会报 `expected str instance, list found`。现在所有文字字段自动合成一句，已保存的旧圣经重跑时也会修正（`director.coerce_text`）。
- 边界：完整流程此前只在替身工具下测过；真实 Flux / LLM 的第一次运行就是「环海石冠」。

#### 2. 星球：场景串成一颗小行星，地势相连

- 平面场景按方位等距投影贴到球面（离场景中心的距离 = 球面弧长，高度 = 半径增量），建筑朝外直立；方形海盘换成整颗哑光海洋球，岸外波纹保留；场景沿倾斜的旅程带绕球排开，高潮在高纬度（`oskar/planet.py`、Blender `compose_planet`）。
- **地势连接，不搭桥**（参考 Oskar「大地势 / 复杂地势生成」）：读相邻两站朝向对方的岛缘高度与间隙 → Oskar 为每段选地势：**阶梯台地**（落差大）、**山脊垭口**（两端都高，两侧山肩夹住通路）、**低地地峡**（两端都低或需要喘息段），并给宽度与垭口高低 → 用同一个 Oskar 引擎生成连接地形，两端伸进岛缘 7 米、顶面对齐岛缘高度 → 与各站同一投影贴上。整合评审时 Oskar 还能用 `link` 操作改某段的地势（`planet.link_specs / link_program`、`director.plan_links`）。
- Godot：云绕星球流动、遇山抬升；海洋球不做碰撞。

#### 3. 游戏组装 ·「星球」方式

- 「游戏组装」页新增「组装方式」，默认「星球」：选两个以上通过验收的场景 → 创建任务。阶段：成果编排 → **星球整合**（Oskar 场景按保存的场景程序重建，得到可站立点 / 通路并套用新的山体色场；其他来源用固定 GLB；地势连接；贴球；导出）→ **星球游戏接入**（Godot）→ 人工试玩确认 → 交付（`planet_assembly.py`）。
- 旧的「关卡串联」方式保留（按顺序切换独立关卡）。

#### 4. 星球游戏：小老虎送信 + 环球有轨电车

- **小老虎**：重力指向球心，贴着球面走；WASD 移动、空格跳、按住鼠标拖动转视角、滚轮拉远拉近；能自动攀上 ≤ 2.3 米的台阶；掉进海里回到最后站稳的地方（`planet_player.gd`，低多边形橙身黑纹小老虎）。
- **每站一封信**：放在从来路一侧能走到的台地上（台阶与坡道算可走，海中孤立岩柱不算），偏高、离来路远；左上角显示「信件 x / N」，收齐提示；夜里信旁有小灯（`planet.game_layout`）。
- **有轨电车**：轨道沿每站岛缘内侧的弧、经地势连接绕星球一圈；高度按地表射线逐点求（滑动中位数 + 净空 + 限坡：岩柱、塔楼处从下面穿过，过海处是带桥墩的高架）；石砌道床、两条钢轨、枕木；电车在每站停靠 5 秒。**靠近电车按 F 上车，车上按 C 切换司机主视角**（司机相机不渲染车身层，没有任何遮挡），**再按 F 下车**（落到最近的可站立点）。E 日光 / 黄昏 / 夜晚，V 开关云（`planet_game.gd`）。
- 多场景世界（星球形态）的 Godot 接入也使用同一套玩法。
- 样例工程：`projects/oskar-trials/planet_game`（十二门徒 · 高山圣城 · 新城，云端构建）。

#### 5. 山体配色：Oskar 色场，从山顶往下纵向铺色

- 学习 x.com/OskSta 2023-10-11「palette authoring tool」视频：一个特征的颜色是由颜色节点张成的色场，每个面在色场里取一个点。逐帧取色得到四个节点：灰绿 #5F8F6A、橙 #D5A157、蓝 #4B8598、玫瑰 #AE6874。
- 岩体取这四色的浅调，**每座山、每根岩柱从自己的山顶往下纵向铺色**：橙 → 玫瑰 → 灰绿 → 蓝（山脚、水线）；横向只做很小的色相偏移；朝天面与亮层带向米白靠；水平层纹明暗交替；悬挑下方压暗；逐面平涂、不加随机。草地同样纵向：黄绿 → 橄榄 → 草绿 → 青绿（`oskar/tint.py`）。
- 颜色写进逐角颜色属性（glTF COLOR_0），Blender 渲染与 Godot 显示一致；场景程序可写 `"tint": 0` 关闭。

#### 6. 控制台：先游玩测试，再下载与发布

- 有 Godot 工程的任务（游戏、星球组装、多场景世界、Oskar 场景）页首出现「▶ 进入游戏试玩」「在 Godot 编辑器中打开」：在本机直接弹出游戏窗口（首次运行先自动导入资源）。
- 试玩确认前，交付页与模型旁不提供下载；点「我已试玩，确认可以发布」后开放下载，并出现「发布」。
- 发布生成 `runs/<任务>/release/`：可玩工程包（Godot 4 打开即玩，附操作说明）；本机装有 Godot 导出模板时，另导出 macOS 应用与 Web 版本（Web 版解压后放到任意静态网站即可在浏览器里玩）。没有模板时如实说明安装方法（`release.py`）。
- 「游戏组装」页顶部「▶ 试玩星球样例」直接运行样例工程。

### Oskar 山形地势专题（2026-10-06）

学习了用户给出的 33 条 Oskar X 帖子（32 条读文字并抽帧，1 条需登录未读），整理为带出处的知识（[学习笔记与落地表](agents/knowledge/oskar/sources/x-terrain-2021-2024.md)，已并入 Oskar 知识档案与顾问技能），并落到引擎与展示工程：

- **山势收分**：低于平滑顶面的岩体沿下坡外放——高处收、低处放，崖面成坡，高岩柱不再“蘑菇化”（`batter`）。
- **轮廓软化**：岩体平面的格网锯齿收成圆润轮廓（`soften`，岩柱 1.2 米、其他 0.8 米）；位移场先平滑再施加，变化率小于 1，不会交叉折面。
- **台缘与地表**：草皮唇边垂过崖缘、内侧一圈灌丛带；草地按低频噪声分三阶明度团块；台面散点降密度。
- **海岸波纹**：水线外 1–2 圈与岸线平行的连续细波纹（等值线生成）。
- **屋顶色域**：屋顶在 roof / roof_b / roof_c 三角色域里取样（主楼用主色）。
- **流动的云、夜间柔光**：Godot 展示工程里云随风漂移、翻山、回绕（C 开关）；E 在日光 / 黄昏 / 夜晚间切换，夜里有大而柔的暖色灯笼与提灯巡逻（`add_lantern`、`add_patrol_light`）。
- **新城参考程序**：`projects/oskar-trials/programs/new-town.ref.json`（海港连拱码头、逐级台地、教堂与钟楼、大台阶）。

验证：用 pip 版 Blender 5.0 在云端按同机位渲染了十二门徒、旧城、新城、水晶城、湖沼的改前 / 改后对照；Godot 4.5 headless 截图核对了云与夜光。Mac 上的 Blender 5.2 / Godot 4.7 尚未复跑。

### Oskar 导演的多场景世界（2026-10-06）

Oskar 不只是一组风格规则，而是亲自用工具做游戏的创作者：先写世界圣经（支柱、色彩角色、共享尺度、旅程节奏），再**亲自画每个场景的目标图**并按自己的评审维度打分、选图、重画；然后**指挥 LLM 在 Blender 里一站一站地建造**，每轮打维度分、比较客观相似度、决定接受还是回滚，自己选下一步是受限修改、推翻重写还是收工；最后把各个场景**排成旅程群岛并接入 Godot**。每次工具调用都以「Oskar → 工具」记入日志。

- **导演档案**：评审维度/权重、阶段顺序、阈值、目标图风格锁、整合原则都写进 `agents/oskar.json` 的 `direction`，随任务快照固定；自定义 Agent 默认继承。
- **趋近过程可见**：「资产与场景」页给出每站的目标图稿次、维度分、趋近曲线（导演分 + 客观相似度，回滚轮为空心点）、逐轮阶段与判定。
- **会学习**：同一世界里前几站的有效/无效改法写进「工作室手记」，带给后面的场景；手记跨任务保存，下一次开工时读取。风格规则仍走审核后应用的学习闭环。
- **门禁**：每站目标图认可、硬检查、导演分和结构相似度，加上世界的尺度/色彩统一、整合评审、Godot 核对，全部通过才交付。

用法与规则见 [使用手册 §18](docs/使用手册.md)。验证边界：编排、接受规则、阶段、布局、门禁与交付已用替身工具测试（`tests/test_atlas.py`）；**尚未用真实模型跑过完整世界**，导演分是否校准需要先试跑核对。星球形态下各站之间由地势连接，并带小老虎送信与有轨电车玩法（见上方总览）。

- **登录与工作台**：首次创建本机账户；总览突出待处理任务，创作记录支持筛选，详情区分执行进度和验收结果。
- **游戏组装**：新增独立选择页，筛选已完成、已有验收通过且 GLB 可用的资产／场景产线。选择关卡、玩家外观和共享道具，调整关卡顺序与目标，创建独立 Godot 组装任务；固定模型副本、来源验收和 Agent 版本，保留原作。自动试玩后还需人工确认完整关卡流程，才能打包。
- **系统 Agent**：查看 Oskar 风格档案，创建自定义 Agent，选择由谁引领创作；任务固定保存当时的规则版本。
- **Oskar 知识融合**：继承 TigerMessenger 的研究，与当前引擎经验合并为 8 组方法、10 份带指纹来源。系统 Agent 的“方法与能力”区分已接入提示词的知识、可执行能力和待移植部分；圣城/岩群图库为融合前的真实引擎样本。
- **统一工作台配色**：根据用户偏好的登录页氛围调整为明亮青色：浅青导航、白色工作面、青色主要操作，登录与工作台保持一致；状态色与作品色板分开。设计依据与对比度见 [配色方案](docs/Oskar工作台配色方案.md)。
- **顾问审阅与改版**：在任务页点击「邀请 Agent 审阅」，选择范围和保留要求。提交时固定方案、验收与最多三张渲染样本；提案包含依据、修改内容和验收办法。单资产改版复制原 GLB（最多 128 MB），重新生成目标、人工确认概念图，再修改与验收；不继承旧通过结论。执行和重跑前校验原模型快照，缺失或改变时停止并报错。
- **学习资料库**：每个 Agent 可导入 UTF-8 Markdown／文本或粘贴资料，保存标题、出处与内容指纹；支持归档和恢复。每次研究可选最多 8 份资料，入队时固定正文，任务页可展开检查。链接用于追溯，尚不自动抓取网页。
- **学习闭环**：从本地参考文档、选定历史作品和研究要求提炼带来源的规则草稿；审核应用后用于新任务，可切换旧版本或恢复基础规则。创作通过后可自动排队复盘。
- **执行资源**：重调用依次调度，服务在调用期间持有租约，预算不足时只驱逐空闲服务；显示队列、耗时与内存估算。
- **质量检查**：缺失证据或必需检查失败时阻止正式打包；提供对应阶段修复入口，建模和组装支持追加迭代。

这里的“学习”是知识与规则提炼，不是模型权重训练。执行目前仍依赖现有本地服务，尚未接入云端算力或自动外部检索。架构与边界见 [Agent 工作台架构](docs/Agent工作台架构.md)。已支持从现有作品邀请指定 Agent 审阅并提出修改建议；对有 GLB 的单资产，可选择视觉或角色建议创建独立改版，原作与受邀时的风格版本保留。完整游戏和场景暂提供提案。改版页可并排核对邀请时的原作证据与新结果，分别列出渲染样本、检查记录和已选建议；不自动判断质量提升。

### 把多条合格产线串成一个游戏

1. 打开侧栏「游戏组装」，或在通过验收的资产／场景任务中点击「加入游戏组装」。页面显示真实可用成果及历史渲染样本；运行结束但验收未通过、模型缺失或仍在执行的任务不能入选。
2. 选择最多 12 条产线（单模型不超过 128 MB，总计不超过 512 MB），分配「关卡场景」「玩家外观」「共享道具」。至少一个关卡、最多一个玩家外观；没有玩家模型时使用默认可控玩家。
3. 用 ↑ ↓ 排列旅程，填写每关目标／出口条件、游戏名称、整体目标，选择引领组装的 Agent。草稿保存在当前浏览器；只读预览可以编排，但不能创建任务。
4. 点击「创建游戏组装任务」。系统再次核对来源，将 GLB 复制到新任务的 `assembly-inputs/`，为同名模型分配独立 ID，保存 `assembly-manifest.json`。复用模型进入 Godot 组装，跳过概念图和重新建模；不会把多个旧工程目录直接拼接。
5. 自动试玩与视觉验收后，打开游戏实际检查所有目标、出口、关卡切换、最终通关和重开，再确认全流程通过。通过交付门禁后，打包新的 Godot 工程、模型、来源清单和报告。原始产线与作品保持独立。

**验证边界：**已验证成果筛选、排序与用途、固定副本、命名冲突隔离、排队、只读保护和独立交付门禁。已有自动试玩只能检查脚本、运行、玩家移动与画面；多关卡玩法由 Agent 编写，效果需要实际运行和人工试玩。本轮没有启动真实多场景组装推理，不能据此声称已生成完整可玩游戏。组装失败可在新任务详情按阶段重试。

## 创作、学习与顾问任务

| 模式 | 阶段 | 使用边界 |
|---|---|---|
| `atlas` 多场景世界 | `atlas_brief → atlas_targets → atlas_scenes → atlas_compose → atlas_godot → deliver` | Oskar 导演全程：出目标图并打分，逐场景趋近（可推倒重写），整合为群岛世界；各站暂无跨岛连接 |
| `assembly` 游戏组装 | `assembly_plan → assemble → review → journey → deliver` | 复用已验收模型，固定来源与顺序；新游戏重新验收，人工确认全部关卡流程后交付 |
| `game` 完整游戏 | `plan → concept → world → model → assemble → review → deliver` | Agent 规则指导世界、角色/道具与玩法构建；资产、世界和最终试玩检查通过才可交付 |
| `oskar` 场景 | `oskar_plan → oskar_build → oskar_godot → deliver` | 必须有目标图；生成带碰撞、轨道相机与日光/黄昏切换的展示工程，玩法需另写 |
| `asset` 单个资产 | `plan → concept → model → deliver` | 新资产默认蓝图，已有源模型自动走 agent 路线 |
| `scene` 旧拆分组装 | `decompose → model → compose → deliver` | SAM 辅助实例拆分与抠图，逐个建模后组装；保留为备选 |
| `consult` 顾问审阅 | `consult` | 固定原作与 Agent 快照，输出待审核提案；符合条件的单资产提案可派生 `asset` 改版 |
| `learn` 风格学习 | `learn` | 提炼规则、保留来源快照、生成待审核版本，不执行游戏打包 |

Oskar 支持岩体、台地、建筑、城墙、拱桥、瀑布、晶簇、大冠树与轨道等原语，以及目标图自动取色。每轮受限修改后做硬检查和客观评分，选择最佳版本导出。游戏世界另提供可站立点和通路数据给 Godot；这尚不等于整张地图的玩法可达性已验证。

## 替代 Astra：在 TigerMessenger 上使用

TigerMessenger 原流程里 Astra 负责“看图 → 在 Blender/Godot 里改 → 截图 → 复核”。本流水线对应的用法：

| Astra 原工作 | 本流水线 |
|---|---|
| 按认可的目标图迭代一个已有资产 | 新建运行 → **单个资产**；上传认可的目标图并勾选“参考图直接作为目标图”；在“源模型路径”填原 `.blend`/`.glb`（先复制到 `runs/<id>/source/`，原文件不动） |
| 生成新的目标概念图 | 单个资产模式不勾选“参考图作为目标”，FLUX 出 3 张候选，Bonsai 选图，控制台人工确认 |
| 多轮“渲染-看图-修改” | 建模阶段自动多轮：每轮固定机位 front/side/persp 渲染 → Bonsai 视觉评审（分数+差异+下一步）→ 硬性检查 → 反馈下一轮；退步自动回退到最佳轮 |
| 把结果接入 Godot | “接入的 Godot 工程目录”填 `TigerMessenger/godot`，交付阶段经人工确认后复制到 `assets/pipeline/<运行ID>/`（新目录，不覆盖；场景引用与玩法验收仍需单独完成） |
| Jev 文本决策 | 评审 JSON（diffs / next_actions）直接驱动下一轮，本地完成，不需要外部 API |

建议每个资产先用 3–4 轮试跑，在“建模”页对比目标图与各轮渲染，再决定是否加轮数或调整通过分。

## 角色与道具的两种建模方式

以下是单资产建模路线；世界和场景另走上述 Oskar 引擎。表中耗时与评分来自早期实测，不代表当前任务的质量保证。

| | 蓝图模式（默认 `model_mode = "blueprint"`） | agent 模式（`"agent"`） |
|---|---|---|
| 做法 | Bonsai 看概念图输出**结构化部件蓝图**（形状/尺寸/颜色/贴合关系），确定性构建器生成模型；评审后修订蓝图 | Bonsai 逐步编写 bpy 代码建模 |
| 每轮耗时（实测） | ~4–6 分钟 | 25–40 分钟 |
| 稳定性 | 确定性构建减少生成代码错误；检测悬空部件；保留各轮蓝图与回退能力 | 易出现 API 误用、部件错位、推倒重来 |
| 实测效果 | 侦察机 2 轮 8.0 通过；小老虎角色 2 轮 5.5 | 侦察机 1 轮 6.5；小老虎 3 轮最高 3.0 |
| 适用 | 新资产（默认） | 迭代已有 .blend/.glb（填了源模型时自动使用）、需要自由几何操作 |

每轮蓝图保存在 `runs/<id>/blueprints/<资产>_rNN.json`，可在控制台“建模”页打开查看。

资产导出默认应用 Oskar 统一外观（平面着色与描边），可用 `oskar_look: false` 关闭。概念图支持多候选；几何建模尚未接入完整的多初稿择优流程。

`scripts/fal_shim.sh` 在 127.0.0.1:8095 提供 fal.ai 兼容的队列接口：图像编辑 / 文生图由 Bonsai 改写指令 + Flux 图生图在本机完成，

## 性能与调参（实测，M5 Max 64 GB）

- Bonsai 2 27B：短上下文解码 ~40–44 tok/s，预填充 ~650 tok/s
- 上下文越长解码越慢（22k token 时降到 ~15–30 tok/s），因此每轮建模/组装都用**全新上下文**（任务 + 目标图 + 当前渲染 + 评审意见），场景状态保存在 Blender/Godot 工程里
- FLUX.1-schnell 4-bit：首张 1024²（含加载）30 s，之后每张约 10 s（概念图阶段实测 11 张 199 s，含选图）；与 LLM 同时推理会明显变慢
- Qwen-Image 2.1 Q6_K（sd.cpp）的历史实测为 768²/20 步 191 s（与 LLM 并发）；当前配置已移除该后端
- MLX 内存必须设上限（`mlx_memory_limit_gb`）：不设时缓冲缓存涨到 49 GB，解码掉到 8 tok/s
- 前缀缓存（APC）默认关闭：命中后解码走分页 KV 路径，~20k 上下文时解码只有 14 tok/s（完整预填充后 32 tok/s）；上下文改由 agent 压缩历史控制
- 相关配置：`[llm.prefix_cache]`、`llm.sampling.tool_step_thinking_budget`、`pipeline.agent_max_steps`

## 评分与验收：已实现能力及限制

- **客观评分已接入**：蓝图与场景迭代使用 DINOv2 / SigLIP-2 辅助比较版本，VLM 差异台账提供修改方向；蓝图通过线另有 `metrics.pass_min_dino` 下限。相似度不等于人工质量评分。
- **分数口径不同**：资产/试玩评审通常为 0–10，DINO/SigLIP 为相似度，Oskar 轮次还有组合客观指标。不要把运行摘要中的这些“分数”直接横向比较；最佳版本以对应 `state.json` 记录为准。
- **保留与回退**：各路线保存蓝图、场景程序、渲染或工程快照，按其冠军选择规则导出；最佳版本不一定是最后一轮，也不一定是文字评审分最高的一轮。
- **统一交付门禁已加入**：四种创作模式共用 `quality.assess()`；核对导出版本的资产验收、游戏最终试玩、世界必需硬检查或场景/Godot 接入记录。缺少必需证据也会阻止正式交付。
- **跨引擎核对**：Oskar 的 Godot 导入、脚本、截图、尺寸与画面相似度保留原检查；相似度服务不可用时记录为未核对，新的正式交付门禁不会把它当作通过。
- **试玩覆盖有限**：当前主要检查短时运行、错误、玩家节点和位移；尚无通用的拾取、投递、胜利条件与全地图可达性测试。
- **目标工程接入有限**：`integrate_to` 经确认后复制 GLB，场景引用与玩法验收仍需另行完成。

目标原则仍是：硬检查不过就不算验收通过，概念图不等于三维完成，GLB 导出不等于游戏已接入。判断现有产物时请同时查看 `state.json` 的检查结果、渲染/截图和 `deliverables/REPORT.md`，不要仅依据运行状态或交付包是否存在。
